# 前端面试题与参考回答

## 使用说明

- 每道题至少包含 4 个部分：问题、考察点、回答依据、参考回答。
- `回答依据` 优先回填前置文档中的事实来源，避免回答脱离项目。
- `参考回答` 可以直接用于练习，但如果项目事实尚未确认，需要把占位内容替换掉。

## 基础题

### 1. 你先整体介绍一下这个项目，包括业务目标和核心技术栈。

- 考察点：能否在 1 到 2 分钟内讲清项目背景、技术选型和整体架构。
- 回答依据：`docs/project-architecture/README.md`、`docs/project-architecture/tech-stack.md`
- 参考回答：这个项目本质上是一个【项目类型】前端应用，核心目标是解决【业务目标】。在技术上我们主要使用【前端框架】+【语言】+【构建工具】这一套组合，路由、状态管理、请求和样式方案分别是【路由方案】、【状态管理】、【数据请求方案】和【样式方案】。这样选型的原因主要是它能兼顾【开发效率 / 可维护性 / 团队协作 / 性能】。从整体架构上看，项目把【页面层 / 组件层 / 业务模块层 / 基础设施层】做了相对明确的分层，所以后续做功能迭代和问题排查都比较顺。

### 2. 当前项目的目录结构是怎么设计的？你觉得这样设计的价值是什么？

- 考察点：是否理解目录职责划分，而不是只会背文件夹名字。
- 回答依据：`docs/project-architecture/project-structure.md`
- 参考回答：这个项目的目录设计重点不是“分多少层”，而是“职责是否清晰”。我会先从入口层开始介绍，比如应用入口、路由入口和全局状态入口分别放在哪里；然后再讲业务模块、通用组件、工具函数、接口封装这些目录是怎么拆开的。这样做的价值主要有三点：第一，大家找代码路径会更快；第二，业务代码和基础能力分离后更容易复用；第三，后续做重构或模块迁移时影响面更可控。如果项目里还做了按领域拆模块，我也会补充说明这样更利于多人协作。

### 3. 这个项目为什么选择现在这套技术方案，而不是其他常见方案？

- 考察点：技术选型背后的判断标准和取舍意识。
- 回答依据：`docs/project-architecture/tech-stack.md`、`docs/project-insights/highlights-and-challenges.md`
- 参考回答：我理解技术选型不能只看“流行不流行”，更重要的是和项目阶段、团队能力、维护成本是否匹配。这个项目选择【当前方案】而不是【备选方案】的原因主要有几个：一是团队当时已经有相关经验，落地成本更低；二是当前方案在【工程化 / 组件化 / 性能 / 生态】上更符合项目诉求；三是如果用备选方案，可能会在【迁移成本 / 学习成本 / 定制复杂度】上带来额外负担。所以最终的选择并不是绝对最先进，而是对当前业务最合适。

## 项目结合题

### 4. 这个项目里你最值得讲的一项技术亮点是什么？你具体做了什么？

- 考察点：是否能把亮点讲成“背景、动作、结果”而不是泛泛而谈。
- 回答依据：`docs/project-insights/highlights-and-challenges.md`、`docs/project-insights/interview-storylines.md`
- 参考回答：如果让我选一个最值得讲的亮点，我会讲【亮点名称】。当时的背景是【业务背景或技术背景】，原来的问题主要在于【性能瓶颈 / 可维护性问题 / 协作问题】。我负责推动的关键动作包括【动作 1】、【动作 2】和【动作 3】。这里最重要的不是“做了很多事”，而是抓住了真正的约束点，比如【关键约束】。最终结果是【结果指标或业务价值】。如果面试官继续深挖，我会再展开我为什么这样设计、踩过哪些坑，以及后续还有哪些优化空间。

### 5. 项目里遇到过什么比较难的问题？你是怎么定位和解决的？

- 考察点：问题分析能力、排查路径和复盘能力。
- 回答依据：`docs/project-insights/highlights-and-challenges.md`
- 参考回答：我一般会按“现象、影响、根因、方案、结果”来讲。这个项目里比较典型的难点是【难点名称】。它带来的直接影响是【影响范围】，比如影响用户体验、开发效率或者线上稳定性。定位时我先看【日志 / 埋点 / 代码链路 / 配置差异 / 复现步骤】，确认问题不是偶发之后，再把可疑链路逐步收敛到【核心根因】。最终方案不是简单修一个点，而是同时处理了【根因修复】和【兜底措施】。这样回答能体现我不是只会救火，而是会把问题彻底闭环。

### 6. 如果让你向面试官证明你真的理解这个项目，而不是只参与了一小部分，你会怎么讲？

- 考察点：对项目全局的掌握程度，以及个人职责边界是否清晰。
- 回答依据：`docs/project-architecture/README.md`、`docs/project-insights/interview-storylines.md`
- 参考回答：我会先明确自己的职责边界，比如我主要负责【模块 / 能力 / 阶段】；然后再说明我对全局的理解，包括项目整体链路、上下游协作关系，以及关键模块之间怎么衔接。这样既不会夸大职责，也能证明我不是只盯着一个页面写代码。接着我会挑一两个关键场景展开，说明我在实际推进里做了哪些判断，比如需求拆解、技术方案设计、联调排查、上线保障和复盘优化。这种讲法比单纯罗列功能点更能体现真实参与度。

## 架构与工程化题

### 7. 项目在工程化方面做过哪些事情？这些事情解决了什么问题？

- 考察点：是否具备稳定交付、规范化和效率优化意识。
- 回答依据：`docs/project-architecture/engineering.md`、`docs/project-insights/highlights-and-challenges.md`
- 参考回答：工程化部分我会从开发效率、质量保障和交付稳定性三个角度来讲。比如项目里如果做了【代码规范 / 提交规范 / CI/CD / 自动化脚本 / 环境隔离 / 构建优化】，我会分别说明它解决的问题。以【某项工程化措施】为例，它直接改善的是【具体问题】，比如减少低级错误、统一协作方式、缩短构建时间或降低发布风险。面试时我会强调这些工作不只是“搭工具”，而是为了让团队在长期迭代里更稳定。

### 8. 如果这个项目后续要继续扩大规模，你觉得现有架构最需要优先优化的点是什么？

- 考察点：架构前瞻性，以及能否识别当前方案的边界。
- 回答依据：`docs/project-architecture/engineering.md`、`docs/project-insights/highlights-and-challenges.md`
- 参考回答：我会先肯定现有架构在当前阶段是有效的，然后再讲它未来可能遇到的边界。比如随着业务继续变复杂，可能会在【模块耦合 / 构建效率 / 状态复杂度 / 组件一致性 / 权限管理】上出现瓶颈。如果只能优先做一件事，我会先优化【优先项】，因为它对【维护成本 / 团队协作 / 线上稳定性】影响最大。这个回答重点不是说当前方案不好，而是体现我知道什么阶段该解决什么问题。

## 性能与优化题

### 9. 你们项目里做过哪些性能优化？效果怎么衡量？

- 考察点：是否能把性能优化讲成可验证的工程动作。
- 回答依据：`docs/project-insights/highlights-and-challenges.md`、`docs/project-architecture/engineering.md`
- 参考回答：我会先区分是首屏性能、运行时性能，还是构建性能，然后再讲具体动作。比如如果做了【按需加载 / 懒加载 / 缓存 / 减少重复渲染 / 包体积治理 / 请求合并】，我会说明它分别针对什么问题。衡量效果时我不会只说“变快了”，而是尽量给出指标，比如【构建时间、资源体积、渲染耗时、接口耗时、错误率】的变化。如果没有完整量化数据，也至少会说明观察口径和用户体感变化。

## 协作与交付题

### 10. 这个项目在多人协作和上线交付方面，你承担了什么角色？

- 考察点：协作意识、推进能力和对交付链路的理解。
- 回答依据：`docs/project-architecture/engineering.md`、`docs/project-insights/interview-storylines.md`
- 参考回答：我在这个项目里不只是写功能代码，也会参与需求评审、方案沟通、联调、提测和上线保障。具体承担的角色可以结合实际项目补充，比如我是否负责过模块 owner、方案推进、问题协调或者上线值守。回答时我会突出两点：第一，我如何让信息在产品、设计、后端和测试之间对齐；第二，我如何在上线前后控制风险，比如灰度、回滚预案、监控观察和问题复盘。这样能体现我对交付结果负责，而不是只对代码负责。
